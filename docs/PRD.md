# 여행 기록 앱 PRD (Paws)

Sep 30, 2026 · @Park Jinyong

## 개요

Paws는 여행의 날짜·장소·사진·글을 한 흐름으로 남기고, 지도 위 동선으로 다시 훑어보는 나 혼자 쓰는 iPhone/iPad 앱이다.

**해결할 문제.** 지금은 사진은 앨범에, 메모는 노트 앱에, 이동 기록은 지도 앱에 흩어진다. 여행이 끝난 뒤 이걸 한 편의 여행기로 합치는 작업이 번거로워서 결국 안 하게 된다. 이 앱은 기록하는 순간 이미 여행기의 구조가 잡히게 만드는 것이 핵심이다.

**목표**

- 현장에서 장소 하나를 기록하는 데 30초 이내 (사진 1장 + 한 줄)
- 여행이 끝나면 Day별 글·사진·지도가 그대로 한 편의 여행기로 읽힌다
- 몇 년 뒤에도 열린다: 데이터는 내 소유이고, 언제든 내보낼 수 있다

**비목표 (v1에서 하지 않는 것)**

- 다른 사람과의 공유, 소셜 기능, 댓글
- 항공·숙소 예약 관리, 길 안내(내비게이션)
- Android, 웹
- 블로그 플랫폼 API를 통한 자동 발행 (수동 발행용 복사는 P1에 포함)

**사용자.** 나 한 명. iPhone은 현장 기록용, iPad는 여행 후 정리와 열람용이다.

**성공 기준**

- 다음 실제 여행 전 기간을 이 앱만으로 기록한다
- 비행기 모드와 로밍 없는 상태에서도 모든 기록 기능이 동작한다
- 여행 후 "다시 정리하는 작업" 없이 그대로 읽어볼 수 있다

## 디자인 방향

Bear의 3단 구조, 차분한 톤, 태그 중심 정리 방식을 뼈대로 가져오고, 지도와 시간축을 얹는다.

첨부된 GitHub 문서(bear.md)는 시각 디자인 가이드가 아니라 Bear의 마크다운 지원 범위를 정리한 표다. 그래서 시각 기준은 스크린샷에서 가져왔다. 아래 색상 값은 근사값 또는 제안값이며, 개발 전에 확정해야 한다.

**에디터(v1).** 블록형이다. 블록 종류는 문단, 소제목, 인용, 체크리스트, 목록, 사진, 위치이고, 글 안의 서식은 굵게와 링크만 지원한다. `#`이나 `**`처럼 문법을 직접 치는 방식은 지원하지 않는다. 마크다운은 내보낼 때 블록에서 변환해서 만든다.

**Bear와 다르게 가는 것.** 지도가 본문과 같은 급의 화면이고, 모든 기록이 날짜 순서 안에 놓이며, 사진이 글 사이에 끼어드는 블록이다.

**타이포그래피.** 한글은 Pretendard, 영문·숫자는 SF Pro(시스템)로 구성한다. 본문 17pt, 줄 간격 1.6, 제목은 굵기로만 위계를 준다.

## 정보 구조

여행(Trip)은 하루(Day)를, 하루는 일정(Stop)을 담고, 사진·글·위치·태그는 모두 일정 하나에 붙는다.

&#91;embedded content: 정보 구조 · Trip → Day → Stop → 4개 요소\]

왼쪽 글자는 iPad 3단 화면에서 각 단계가 보이는 자리다. 지도는 Day의 일정들을 시간순으로 이어서 그린다.

## 필수 기능

요청한 네 가지를 모두 v1에 넣는다. 핵심 단위는 **일정(Stop)** 하나이고, 사진·글·좌표는 모두 일정에 붙는다.

### F1. 일자별 여정 기록

- 여행(Trip)을 만들 때 제목, 시작일, 종료일, 커버 사진을 정한다. 기간에 맞춰 Day가 자동으로 생긴다
- Day는 날짜와 이모지, 제목을 가진다 (예: "Day 3 · 교토"). 제목은 직접 고칠 수 있다
- 일정은 장소(검색, 현재 위치, 지도에서 핀 찍기), 시각, 본문, 사진, 태그로 이루어진다
- 일정은 시각순으로 자동 정렬되고, 드래그로 순서를 바꿀 수 있다
- 지난 날짜에 소급해서 추가할 수 있다
- 완료 기준: 여행 화면에서 일정 하나를 만드는 데 3탭 이내(＋ → 장소 → 저장)

### F2. 일정별 사진 추가

- 사진 보관함에서 여러 장 선택하거나 카메라로 바로 촬영해 일정에 붙인다
- 사진은 본문 안에 글 사이 블록으로 넣을 수 있고, 일정 상단에는 대표 사진 1장을 지정한다
- 사진마다 촬영 시각과 위치(EXIF)를 읽어서 저장한다
- 앱은 긴 변 2048px로 줄인 사본을 자체 보관한다. 사진 앱에서 원본을 지워도 기록은 남는다
- Live Photo는 정지 이미지로 저장한다
- 완료 기준: 한 번에 20장 추가, 비행기 모드에서도 동작

### F3. 일정별 메모/블로그 기록

- 일정 하나의 본문이 메모이자 블로그 글이다. 한 줄로 시작해서 나중에 길게 이어 쓸 수 있다
- 블록형 에디터(브런치 방식)에 하단 플로팅 툴바를 쓴다. 문단, 소제목, 인용, 체크리스트, 목록, 사진, 위치 블록을 쌓는 구조이고, 글 안에서는 굵게와 링크만 지원한다
- 본문 안에 사진 블록과 위치 블록을 넣을 수 있다
- 자동 저장, 실행 취소, 앱이 꺼져도 작성 중인 글이 남는다
- **읽기 모드**: Day 또는 여행 전체를 일정 순서대로 글 + 사진 + 미니 지도로 이어서 보여 주는 읽기 전용 뷰이며, 여기서 블로그 발행용으로 복사할 수 있다. 이것이 "여행 후 정리 없이 바로 읽히는 여행기"를 만든다
- 완료 기준: 3,000자 글과 사진 10장이 있는 일정에서도 스크롤이 끊기지 않는다

### F4. 위치를 잇는 지도

- Day 지도: 그날의 일정 핀을 시간순 번호로 표시하고 선으로 잇는다
- 여행 지도: 전체 동선을 보여 주고, Day별로 선 톤을 구분한다
- 핀을 누르면 해당 일정 카드가 열리고, 목록에서 카드를 누르면 지도가 그 위치로 이동한다
- 좌표는 일정을 만들 때의 GPS 또는 검색한 장소에서 가져오고, 지도에서 핀을 끌어 고칠 수 있다
- 완료 기준: 하루 일정 10개가 있는 Day 지도가 1초 안에 그려진다

## 추가 제안 기능

P1 다섯 개는 v1에 함께 넣기를 권한다. 앞의 두 개가 없으면 "현장 30초 기록"이라는 목표가 지켜지지 않는다.

| 우선순위 | 기능 | 내용 | 필요한 이유 |
| --- | --- | --- | --- |
| P1 | 사진으로 일정 자동 생성 | 사진 여러 장을 고르면 촬영 시각과 위치로 묶어 일정 초안을 만든다 | 여행 중엔 사진만 찍고, 정리는 저녁에 한 번에 하는 습관에 맞다 |
| P1 | 빠른 기록 진입점 | 잠금화면 버튼, 위젯, 액션 버튼에서 앱을 열지 않고 "지금 위치 + 사진 1장" 일정을 만든다 | 앱을 여는 순간 기록이 귀찮아진다 |
| P1 | 전체 검색과 태그 | 글, 장소, 태그를 한 번에 검색하고 태그로 필터한다 | Bear의 핵심 경험이고, 여행이 쌓일수록 필요해진다 |
| P1 | iCloud 동기화 | iPhone에서 쓴 기록이 iPad에 자동으로 나타난다 | iPhone·iPad 대응이 필수이므로 사실상 필수 기능이다 |
| P1 | 내보내기 + 블로그 발행용 복사 | 여행 하나를 마크다운 + 이미지 폴더로 내보내고, 읽기 모드를 네이버 블로그·브런치에 붙여넣기 좋은 형태로 복사한다 | "몇 년 뒤에도 열린다"는 목표를 지키고, 외부 블로그 발행 계획을 지원한다 |
| P2 | 이동 경로(GPS 트랙) 기록 | 옵션을 켜면 이동 중 위치를 저전력으로 기록해 실제 이동선을 그린다 | 핀 사이의 실제 동선이 보인다. 다만 배터리·프라이버시·구현 비용이 크다 |
| P2 | 계획 모드 | 미래 날짜의 일정을 "예정"으로 만들고, 다녀온 뒤 "기록"으로 바꾼다 | 계획과 기록이 같은 구조를 쓰면 이중 입력이 없다 |
| P2 | 경비 메모 | 일정에 금액과 통화를 붙이고 Day·여행 합계를 낸다 | 여행 후 지출 정리를 따로 하지 않아도 된다 |
| P2 | 잠금 (Face ID) | 앱 전체 또는 특정 여행을 생체 인증으로 잠근다 | 개인 일기 성격의 기록이 섞인다 |
| P2 | PDF 여행기 | 읽기 모드 그대로 PDF로 내보낸다 | 인쇄와 보관용 |
| P3 | 날씨 자동 기록 | Day에 그날의 날씨를 자동으로 붙인다 | 있으면 좋은 정도 |
| P3 | "N년 전 오늘" 알림 | 과거 같은 날 일정을 알려 준다 | 앱을 다시 열게 하는 장치 |
| P3 | 여행 통계 | 방문 도시 수, 이동 거리, 사진 수를 보여 준다 | 재미 요소 |

**판단.** GPS 트랙 기록은 매력적이지만 v1에서 빼는 것이 맞다. 핀을 시간순으로 잇는 것만으로도 "동선"은 충분히 보이고, 트랙 기록은 배터리와 백그라운드 권한 설계가 따로 필요하다. 필수 기능이 안정된 뒤에 P2로 붙인다.

## 플랫폼: iPhone과 iPad

iPhone과 iPad는 하나의 유니버설 앱으로 만들고, 화면 폭에 따라 Bear처럼 1단·2단·3단으로 바뀐다.

| 항목 | iPhone | iPad |
| --- | --- | --- |
| 기본 용도 | 현장 기록: 빠른 일정 추가, 사진 촬영 | 여행 후 정리와 읽기: 긴 글 쓰기, 사진 정리 |
| 화면 구성 | 세로 우선. 여행 목록 → Day·일정 목록 → 일정 에디터를 화면 전환으로 이동 | 가로는 3단(사이드바 / 일정 목록 / 에디터), 세로는 2단 |
| 지도 배치 | Day 화면 상단 미니 지도 + 전체 화면 지도. 지도 위에 일정 카드가 올라오는 하프 시트 | 세 번째 열이 대상에 따라 바뀐다. Day를 고르면 Day 지도, 일정을 고르면 에디터(상단에 접이식 미니 지도). 4번째 패널은 두지 않는다 |
| 에디터 | 하단 플로팅 툴바, 한 손 입력에 맞춘 큰 버튼 | 같은 툴바 + 하드웨어 키보드 단축키 (⌘N 새 일정, ⌘F 검색, ⌘B 굵게 등) |
| 사진 입력 | 카메라 촬영, 사진 보관함 선택 | 사진 앱에서 드래그 앤 드롭, 보관함 선택 |
| 멀티태스킹 | 해당 없음 | Split View, Slide Over, Stage Manager에서 레이아웃이 깨지지 않는다 |
| 공통 | 다크 모드, Dynamic Type, VoiceOver 기본 지원 | 동일 |

**최소 OS 버전.** 본인 기기에 설치된 iOS·iPadOS를 최소 지원 버전으로 정한다. 나 혼자 쓰는 앱이므로 하위 버전 호환에 시간을 쓰지 않는다.

**iPad 지도 배치 (제안).** 지도를 토글이나 4번째 패널로 두지 않고, 보고 있는 대상에 따라 세 번째 열을 바꾼다. Day를 고르면 Day 지도가 열려 그날의 동선을 훑고, 일정을 고르면 에디터가 열리며 상단에 접이식 미니 지도가 붙는다. 4열은 11인치 가로(폭 약 1,200pt)에서 에디터가 너무 좁아져 제외했다. 글과 지도를 동시에 봐야 할 때를 위해 툴바에 "에디터 | 지도" 2분할 버튼을 두고, 이때 일정 목록 열은 접는다. 세로 모드와 Split View에서는 지도가 시트로 올라온다.

## 데이터 모델과 저장

데이터는 기기 안에 먼저 저장하고, iCloud가 기기 간 복사를 맡는다. 본문은 블록 목록으로 저장하고, 마크다운과 블로그용 HTML은 내보낼 때 블록에서 변환한다.

| 엔티티 | 주요 필드 | 관계 |
| --- | --- | --- |
| Trip | 제목, 이모지, 시작일, 종료일, 커버 사진, 고정 여부 | Day를 여러 개 가진다 |
| Day | 날짜, 제목, 이모지 | Trip에 속하고 Stop을 여러 개 가진다 |
| Stop (일정) | 장소명, 위도, 경도, 주소, 시각, 시간대 ID, 정렬 순서, 본문(블록 목록), 대표 사진 | Day에 속하고 Photo와 Tag를 가진다 |
| Photo | 이미지 파일(2048px 사본), 촬영 시각, EXIF 위도·경도, 가로·세로, 정렬 순서 | Stop에 속한다 |
| Tag | 경로형 이름 (예: 음식/라멘) | Stop과 다대다. 일정의 태그 칩으로 직접 입력 |
| Track (P2) | 좌표와 시각의 배열 | Trip에 속한다 |

**저장 규칙**

- 시각은 절대 시각과 현지 시간대 ID를 함께 저장한다. 해외에서 오후 3시에 쓴 기록이 귀국 후 한국 시간으로 바뀌어 보이는 문제를 막는다
- 본문은 블록(문단, 소제목, 인용, 체크리스트, 목록, 사진, 위치)의 순서 있는 목록으로 저장한다. 사진 블록은 사진 ID를 가리킨다. 마크다운과 블로그용 HTML은 이 블록을 순서대로 변환해서 만든다
- 이미지 파일은 데이터베이스 밖 별도 파일로 두고, DB에는 경로만 넣는다
- 삭제는 30일간 휴지통에 보관한 뒤 지운다 (Bear의 Trash와 같은 방식)
- 동기화 충돌은 필드 단위 "마지막 수정이 이김"으로 처리한다. 혼자 쓰는 앱이라 이 정도로 충분하다

## 기술 스택 제안

iPhone·iPad 전용이고 사용자가 나 한 명이므로, 크로스플랫폼 없이 SwiftUI 네이티브로 가는 것을 권한다. iCloud 동기화, 사진, 위치, 위젯이 모두 애플 프레임워크 안에서 해결된다.

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| UI | SwiftUI 유니버설 앱, NavigationSplitView | 하나의 코드로 1단·2단·3단 레이아웃을 처리한다 |
| 저장 | SwiftData (필요하면 Core Data) | 로컬 우선 저장, CloudKit과 바로 연결된다 |
| 동기화 | iCloud (CloudKit 개인 데이터베이스) | 서버를 직접 운영하지 않는다 |
| 지도 | MapKit (SwiftUI Map) | 무료, 경로선과 핀이 기본 제공된다 |
| 위치 | CoreLocation | 현재 위치와 (P2) 저전력 이동 기록 |
| 사진 | PhotosPicker, 카메라(AVFoundation), ImageIO(EXIF) | 촬영 시각·위치를 읽고 리사이즈 사본을 만든다 |
| 에디터 | SwiftUI 블록 목록 (블록마다 TextEditor, 굵게·링크는 AttributedString) | 블록 단위라 한글 입력 중 서식을 다시 입히는 문제가 없고, 구현이 단순하다 |
| 빠른 기록 | WidgetKit, App Intents | 잠금화면·액션 버튼에서 일정 생성 |
| 배포 | Xcode로 본인 기기에 설치, TestFlight | 앱스토어 심사가 필요 없다 |

**먼저 알아둘 조건**

- Mac, Xcode, 유료 Apple Developer 계정을 이미 갖고 있어 바로 착수할 수 있다
- 유료 계정이 있으므로 iCloud(CloudKit) 동기화를 처음부터 켜고 개발한다
- Apple Maps의 국내 장소 검색 품질은 프로토타입 단계에서 먼저 확인한다. 부족하면 장소 검색만 다른 서비스로 바꾼다

**대안.** React Native나 Flutter도 가능하지만 Android가 필요 없고, 동기화·위젯·에디터에서 네이티브 대비 이점이 없다.

**개발 방식.** Swift/SwiftUI 경험 없이 Claude Opus 5.5와 Sonnet 5.5로 바이브코딩한다. 그래서 기능을 작은 단위로 나눠 한 번에 하나씩 만들고, 만들 때마다 iPhone·iPad 실기기에서 직접 써 보며 증상을 그대로 전달하고, 단계마다 Git 커밋으로 되돌아갈 지점을 남긴다.

## 비기능 요구사항

해외 여행 중 로밍 없이 쓰는 상황이 기준이다. 오프라인 동작, 데이터 안전, 배터리를 먼저 챙긴다.

| 항목 | 기준 |
| --- | --- |
| 오프라인 | 일정 생성, 사진 추가, 글쓰기, 열람은 모두 네트워크 없이 동작하고, 연결되면 자동 동기화된다 |
| 오프라인 지도 | MapKit은 앱이 지도를 미리 내려받는 기능을 제공하지 않는다. 배경 지도는 캐시된 범위만 보이고, 핀·경로선·기록은 항상 보인다 |
| 속도 | 앱 실행 후 새 일정 저장 화면까지 2초 이내. 사진 20장 추가 중에도 화면이 멈추지 않는다 (리사이즈는 백그라운드 처리) |
| 규모 | 여행 1개에 일정 300개, 사진 2,000장이어도 목록 스크롤이 부드럽다 |
| 저장 공간 | 사본 1장을 0.5\~1MB로 가정하면 사진 2,000장은 약 1\~2GB다 (추정). iCloud 저장 공간 여유를 미리 확인한다 |
| 배터리 | 위치는 일정을 만들 때 1회만 조회한다. 백그라운드 추적은 P2에서 옵션으로만 제공한다 |
| 프라이버시 | 데이터는 내 iCloud 개인 영역에만 있다. 분석·광고 SDK를 넣지 않는다. 사진은 "선택한 사진만 허용" 상태에서도 동작한다 |
| 데이터 안전 | iCloud 동기화는 백업이 아니다 (삭제도 그대로 전파된다). 30일 휴지통과 수동 내보내기로 보완한다 |
| 안정성 | 작성 중인 글은 자동 저장되고, 앱이 강제 종료돼도 복구된다 |
| 언어 | v1은 한국어 UI만 지원한다 |

## 리스크와 결정 사항

가장 위험한 것은 에디터다. 나머지는 기능 하나가 밀리는 수준이지만, 에디터는 앱의 완성도 전체를 좌우한다.

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 블록 에디터의 굵게·링크 서식과 블록 간 이동 | 여전히 가장 손이 많이 가는 부분이다 | M0에서 에디터만 먼저 프로토타입한다. 어려우면 굵게·링크를 빼고 블록 서식만 남긴다 |
| CloudKit 스키마는 배포 후 수정이 까다롭다 | 나중에 필드를 바꾸기 어렵다 | 처음부터 iCloud를 켜고 개발하고, M0 끝에 데이터 모델을 확정한다 |
| MapKit의 국내 장소 검색 품질 | 원하는 가게가 검색되지 않을 수 있다 | 프로토타입에서 실제 장소 10곳을 검색해 보고 판단한다 |
| 사진 용량 | iCloud 무료 용량을 넘길 수 있다 | 2048px 사본만 보관하고, 용량을 보여 주는 화면을 둔다 |
| 블로그 붙여넣기 시 서식·사진 손실 | 네이버 블로그·브런치 에디터에서 서식이나 사진이 깨질 수 있다 | M0에서 두 에디터에 실제로 붙여넣어 보고 발행용 형식을 확정한다 |

**결정 사항**

| 항목 | 결정 |
| --- | --- |
| 앱 이름 | Paws |
| 개발 환경 | Mac, Xcode, 유료 Apple Developer 계정 보유 |

| iPad 지도 | 3번째 열이 Day 지도와 에디터로 바뀌는 방식 (플랫폼 섹션 참조) |

**블로그 발행 방식.** 앱에서 블로그로 자동 발행하는 방식은 권하지 않는다. 네이버 블로그의 글쓰기 API는 2020년 5월에 종료됐고([관련 보도](https://www.newspim.com/news/view/20200413000737)), 브런치는 공개된 발행 API를 확인하지 못했다. 그래서 읽기 모드에서 제목·본문·사진 순서가 살아 있는 서식 글을 복사하고 사진을 함께 저장하는 "발행용 내보내기"로 설계한다. 두 에디터에 붙여넣었을 때 서식과 사진이 어떻게 남는지는 M0에서 실제로 시험해 확정한다.
